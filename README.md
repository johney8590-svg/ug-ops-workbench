## 一、先看這裡：資安風險與需要資訊部配合的事

上線前請把這一節交給資訊部審核。以下是我已知的風險，沒有隱瞞的部分。

**1. 後端網址是公開的。** Apps Script 網頁應用程式必須設成「任何人」才能讓手機呼叫，所以網址本身沒有保護力，保護靠的是程式裡自己做的帳號密碼登入。這不是公司的單一登入（SSO），也沒有雙重驗證。
**2. 密碼防護的強度有限。** 密碼以「加鹽 SHA-256」雜湊後存放（Apps Script 沒有 bcrypt 這類慢速雜湊）。如果資料試算表外流，弱密碼有被暴力破解的可能。因應：試算表不要分享給任何人、初始密碼為 10 碼隨機、強制首次登入改密碼。
**3. 登入失敗鎖定可被濫用。** 同一帳號連錯 5 次鎖 15 分鐘。知道帳號的人可以故意讓某人暫時登不進來。
**4. 登入憑證存在手機瀏覽器。** 有效 30 天。手機遺失時，請用選單「重設某人的密碼」，該員所有登入狀態會立即失效。
**5. 行事曆訂閱網址等於鑰匙。** 拿到網址的人可以看到該員的行程（只有行程，沒有其他資料）。可在畫面上重設。
**6. 資料放在部署者的 Google 帳號。** 請用公司的 Google 帳號建立試算表與部署，不要用個人帳號。離職交接時所有權要能移轉。
**7. 回報照片可能拍到人。** 照片存在指定的 Drive 資料夾，只有擁有者能直接開啟，同仁只能透過工作台、且僅限自己門市或自己部門的單才能看。資料夾請不要另外分享。
**8. 稽核紀錄。** 登入、寫入、改密碼都會記在 `log` 分頁（帳號、動作、時間），不記密碼與內容全文。

**需要資訊部確認或配合：**
- 這套（公開網址＋自建登入）是否符合公司對內部系統的規範；若不符合，正式版應移到公司伺服器並接公司帳號登入。
- GitHub Pages 的程式碼庫是公開的。裡面沒有金鑰與真實資料，但程式邏輯看得到，請確認可接受，或改用私有庫＋公司主機。
- 資料保存期限、備份方式、離職帳號停用流程（目前是把 `people` 分頁的 `active` 清空）。

**我不確定、需要實機驗證的地方**寫在第五節。

## 二、部署步驟（約 30 分鐘）

1. 用公司 Google 帳號新增一份試算表，命名「UG 營運工作台資料」。**不要分享給任何人。**
2. 試算表選單「擴充功能 → Apps Script」。把 `backend/` 的 7 個 `.gs` 檔依檔名各建一個檔案貼上。到「專案設定」勾選「顯示 appsscript.json」，把內容換成 `backend/appsscript.json`。
3. 「專案設定 → 指令碼屬性」新增：

   | 屬性 | 值 | 必填 |
   |---|---|---|
   | `DASHBOARD_SHEET_ID` | 營運儀表板後台試算表的 ID（網址 `/d/` 後面那串） | 是 |
   | `DASHBOARD_TAB` | 逐日明細的分頁名稱，預設 `data` | 否 |
   | `PHOTO_FOLDER_ID` | 放回報照片的 Drive 資料夾 ID；不設就不存照片 | 建議 |
   | `NOTIFY_EMAIL` | 填 `on` 才會在回報、催辦時寄信給處理單位（要在 `people` 填 email） | 否 |
   | `TARGET_BASE_FROM`／`TARGET_BASE_TO`／`TARGET_GROWTH` | 暫行目標的基期與成長率，預設 2026-09-01／2026-10-31／0.05 | 否 |

   儀表板資料分頁需要有 `store`、`date`、`revenue` 三欄（`zone` 選填），一列是一間店一天。工作台對它**只讀不寫**。
4. 重新整理試算表，上方會多一個「UG 工作台」選單，依序執行：
   - **① 建立資料分頁**（第一次會跳出授權畫面）。完成後到 `people` 分頁確認名單：`role` 填 `director`、`supervisor` 或 `dept`；部門窗口的 `dept` 要跟處理單位名稱一致（工務、採購、行銷、營運後勤）。
   - **② 從儀表板帶入門市**，然後在 `stores` 分頁的 `supervisor` 欄填上負責督導的**帳號**。
   - **③ 產生初始密碼**。密碼會出現在「初始密碼」分頁，個別私訊給同仁後**把該分頁刪掉**。
5. Apps Script 右上「部署 → 新增部署作業 → 網頁應用程式」：執行身分「我」、存取權「任何人」。複製結尾是 `/exec` 的網址。
6. 把網址貼進 `docs/config.js` 的 `API_URL`，再把 `docs/` 四個檔案放上 GitHub Pages。
7. 之後改了 `.gs` 要「部署 → 管理部署作業 → 編輯 → 新版本」才會生效。

**選填的資料分頁**
- `qsc`：iService 的 QSC 結果（store、date、score、by、fails 以頓號分隔）。門市頁會顯示上次分數與未達標項目。目前要手動貼上。
- `specials`：要從目標基期扣掉的特殊業績（store、date、amount、note）。

## 三、這一期做了什麼

**督導**
- **我的門市**：自己負責的店，依「需要處理的程度」排序（落後區域、連兩週下滑、逾期待辦、太久沒關心），今天行程要去的店排最前面。
- **門市頁**：昨日營收與比較、月累計對暫行目標、本週抽查進度、QSC 上次未達標項目、未結案待辦（可催辦、補充）。
- **拍照回報**：一句話＋照片。系統自動判斷給工務／採購／行銷／營運後勤；同店同類 14 天內已有未結案的單會先提醒，可併入原單或另開。
- **訪店紀錄**：現場、遠端共用一張表。遠端抽查選時段、上傳截圖帶入影像時間，由伺服器判斷是否計入（開班 11:00 前、營業中 10:00–21:00、閉店 20:00 後，且是本週的畫面）。只催辦沒寫紀錄就離開，也會自動留一筆。
- **週誌**：數字由系統帶入，文字由本週紀錄自動整理成草稿，確認補充後送出；看得到營運經理回覆。
- **行程**：週檢視、新增／修改／刪除自己的行程；可訂閱到手機行事曆，之後自動更新。

**營運經理**：晨報（昨日營收、需關注門市、逾期待辦、超過 7 天沒關心的門市、今日動態）、切換檢視任一督導的畫面、週誌審閱與回覆、批次排程（多人、多日、每週固定星期）。

**部門窗口**：只看到自己部門的待辦，可受理、回覆、結案。

**規則出處**：需關注＝相對區域平均落後 10% 以上，或連續兩週下滑；暫行目標＝9、10 月各星期別平均日營收（扣特殊狀況）× 1.05，依當月實際星期組成換算。

## 四、這一期沒有做的（重要）

- **還沒有跟既有的修繕、物料異常、文宣申請系統連動。** 現在的回報只存在工作台自己的 `todos` 分頁。也就是說上線後會暫時有兩個入口，督導在工作台回報的修繕，工務在原本的修繕系統看不到，要到工作台（或收通知信）才看得到。要打通需要知道那三套系統的後台資料放在哪、能不能寫入。在打通之前，建議先只讓督導試用「訪店紀錄、週誌、行程」，回報功能等連動後再開。
- **截圖時間不是從畫面辨識的。** 目前取照片的拍攝時間或檔案時間，督導也能手動改，所以它防的是「忘記」不是「造假」。截圖本身這一期也沒有留存。要做到辨識監視器畫面上的時間戳記，需要資訊部評估。
- **QSC 沒有自動同步**，要等確認 iService 能否匯出。
- **LINE@ 推播、版本公告、工作看板、案件中心**在第二期。
- **香港門市的幣別**：晨報的「昨日營收」是所有門市直接加總。若儀表板裡香港是港幣，這個總數會失真，需要你告訴我儀表板怎麼處理。

## 五、驗證狀況

**已在本機驗證**（`dev/` 裡的模擬環境直接執行這些 `.gs` 檔）：
- 後端 90 項：登入與鎖定、三種角色的權限邊界（督導看不到別人的門市與照片、部門不能結別部門的單、非營運經理不能排別人的行程）、抽查時段判斷、回報去重、週誌自動整理、行事曆內容、初始密碼流程。
- 手機畫面 35 項（iPhone 尺寸）：三種角色的完整操作流程、沒有水平捲動、輸入的 HTML 不會被執行、瀏覽器沒有錯誤。

**還沒驗證，部署後請實測**（模擬環境不等於真的 Google）：
1. 手機瀏覽器跨網域呼叫 Apps Script 是否順利（做法是業界常見的，但我沒有在你的帳號上跑過）。
2. 行事曆訂閱：Apps Script 會先轉址再回傳內容，iPhone 行事曆通常沒問題，**Google 日曆的「透過網址新增」對這種轉址不一定穩定**，請兩種手機各試一次。
3. 儀表板資料分頁的實際欄位名稱與資料量。資料很大時第一次開會慢（之後 30 分鐘內有快取）。
4. 每次操作大約要等 1–3 秒（Apps Script 的正常速度）。
5. 寫入試算表時「開頭是 = 的文字不會變成公式」的防護，在真的試算表上請用一筆 `=1+1` 的溝通重點確認。
6. Drive 照片存取與寄信的授權範圍。

## LINE 通知（選用，預設關閉）

會推播的事：督導請營運經理協助 → 營運經理；營運經理回覆協助 → 原提出人；催辦 → 該處理單位；公告核定 → 所有同仁；公告待核定 → 營運經理；週誌回覆 → 該督導。

啟用步驟（都要由帳號擁有者本人操作）：

1. 在 LINE Developers 建 Messaging API channel，發一組 Channel access token。
2. Apps Script 新增 `14_LineSend.gs` 的內容（平常部署**不含**這個檔），存檔後執行一次 `checkSetup`，Google 會要求授權「連線到外部服務」，按允許。**還沒按允許前，工作台可能暫時無法使用，請挑離峰時間做。**
3. 指令碼屬性加 `LINE_TOKEN`（貼 token）與 `APP_URL`（工作台網址，會附在訊息後面）。
4. 建立新版本部署；到 LINE Developers 把 Webhook URL 設成 Web App 的 `/exec` 網址並開啟 Use webhook。
5. 同仁到工作台「我的帳號」→ 取得綁定碼 → 加官方帳號好友 → 傳「綁定 123456」。

資安說明：
- Token 只放在指令碼屬性，不進前端、不進版本庫。
- Apps Script 讀不到 LINE 的簽章標頭，**無法驗證 webhook 真的來自 LINE**。因此 webhook 只做一件事：用一次性綁定碼（6 位數、10 分鐘、只有登入者看得到）把 LINE 帳號綁到工作台帳號。偽造的請求沒有綁定碼就無法做任何事，也讀不到任何資料。綁定碼被猜中的機率約百萬分之一／次；若資訊部要求簽章驗證，需改由公司伺服器或 Cloudflare Worker 轉接。
- 推播內容會經過 LINE 的伺服器（門市名、案件摘要），不含營收數字與個資。免費官方帳號每月推播則數有上限，超過就收不到。
- 正式啟用前請資訊部審核。

## 速度

- 前端：上次的畫面資料會留在裝置的 localStorage，下次打開先顯示再背景更新（頂端細線＝更新中）；登入後用一次 `batch` 連線把其他分頁先抓好，切換分頁不用等。登出或登入過期會清掉。**裝置上因此會留有最近一次看到的營運資料，共用裝置請記得登出。**
- 後端：每個分頁暫存 1 小時、排程每 30 分鐘重讀；經由程式的寫入立刻清暫存。直接在試算表手動改資料最慢 30 分鐘生效，要立刻生效就從編輯器執行一次 `checkSetup`。

## 帳號密碼現況（2026-11-27）

依營運經理決定，全部帳號先設成同一組共用密碼、不強制第一次登入變更（`setAllPasswordsKeep`，密碼由擁有者放在指令碼屬性 `TEMP_PASSWORD`，執行後自動刪除）。**風險：工作台網址公開、帳號是名字，知道共用密碼的人可以登入任何人的帳號（含營運經理）。** 建議盡快請每個人到「我的帳號」改成自己的密碼；資訊部審核前應改回強制變更（`setAllPasswords`）。
